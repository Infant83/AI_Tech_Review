# 운영팀(ADOPT) 과제 일정표

에이전틱 개발운영팀(Agentic DevOps Team, ADOPT)의 현재 운영 주기와 과제별 예정 시각을 이 문서에서 관리한다. 원인은 일감, 실제 실행·검증·배포는 기존 실행 기록에 남긴다. 일정표를 완료 증거나 자동 잠금으로 사용하지 않는다. 모든 시각은 **한국시간 Asia/Seoul(+09:00)**이다.

## 현재 운영 주기

- 기존 `ai-tech-review` 예약 하나를 사용한다. 기본은 매일 **03·11·19시**다.
- **2026-11-12~11-18 임시 증편:** 매일 **03·07·11·15·19시**, 하루5회. 낮에는4시간 간격이고19→03시는8시간이다.
- **2026-11-19 첫 이용 가능한 회차:** 적체·재발·실행 지연·기록 부담을 재평가한다. 이후 사용자의 연장 지시가 없으면 같은 예약을 기본3회로 복귀시키고 이 표·예약 지침을 함께 갱신한다. 별도 복귀 예약은 만들지 않는다. 실행 호스트가 이용 불가하면 복귀 역시 실제 다음 실행 때 처리하고 늦어진 사실을 남긴다.
- 11/12 03시 실행은 기존 기록을 재사용한다. 07시는 증편 설정 이전에 경과했으므로 소급 실행·누락 완료로 기록하지 않는다. **변경 후11/12 11시·15시·19시,11/13 03시·07시 근접 회차는 각각11:00:31.188·15:01:46.064·18:55:50.197·02:59:57.141·07:00:03.001에 실제 기동했다.** 서로 다른 날짜의 다섯 시각 첫 기동을 확인했으며, 기간 전체의 지속·정각 실행을 보증하지 않는다.
- 회차는 재개 기회다. 다섯 시각마다 새 과제·전체 검사·배포를 만들지 않는다. 새 자료 없는 정상 점검은 조용히 기록하고 완료·실패·중대한 변화·필요한 결정만 알린다.

## 새 요청과 긴급 작업의 우선순위·슬롯 재배정

1. **접수 시와 회차 시작에 재판정한다.** 기존 일감과 중복·재발인지, 기술/편집 어느 책임인지 확인한다. 최신 사용자의 구체적인 우선순위 지시를 우선하며, 허용된 재배정 범위에서 영향·시급성·신뢰할 만한 근거·의존 관계·수정/중단 위험·대기 기간을 판단한다. 우선순위 원본은 해당 일감의 priority이며, 위 실행 큐와 과제별 배정은 그 판단을 반영한다. 콘텐츠 판단·일정은 편집부(AEDAUT)의 권한을 유지한다.
2. **P0는 발견한 실행에서 우선 확인·완화한다.** 광범위한 장애·손실·노출이 확인됐거나 영향이 큰 신뢰할 만한 제보를 받은 경우, 원인 미확정을 이유로 확인을 미루지 않는다. 제보·확인 중·실제 장애는 구분하고 기존 권한과 복구 경계 안에서 대응한다. P1은 가장 빠른 안전한 가용 슬롯으로 앞당긴다. 정상 작업의 정해진11시/19시 역할이 긴급 대응을 막지 않는다. 진행 중 대화에서 요청을 받았거나 회차에서 발견했을 때의 대응이며, 회차 사이의 상주 감지·자동 기동을 새로 구현한 것은 아니다.
3. **진행 작업을 보존하고 전환한다.** 수정 범위·기준 커밋·작업 사본·현재 후보/검증 상태·저장 대기·재개 지점을 확인해 인계한다. 미검증 변경을 main에 급히 합치거나 다른 작업의 파일/필기를 버리지 않는다. 안전한 중단은 기존 과제의 모든 검사를 끝낼 때까지 긴급 확인을 미룬다는 뜻이 아니다. 이미 배포가 진행 중이면 실제 단계·현재 공개본·중복 알림/구판 위험을 먼저 확인하고 기존 직렬 경로에서 완화·복구한다. 무조건 취소·재실행하거나 두 배포를 경쟁시키지 않는다.
4. **구현·검증·통합 슬롯을 함께 다시 배정한다.** 현재5회(기간 종료 뒤 기본3회)의 기존 슬롯 안에서 담당·운영순서·구현/독립 검증/통합 시각을 정한다. 긴급 작업으로 밀린 과제에는 다음 재개 또는 검토 시각을 반드시 남기고, 선후행 과제의 시각·공통 파일 담당도 함께 조정한다. 즉시 처리 중인 긴급 작업은 실제 착수 시각을 기록하며 다음 정규 슬롯은 후속 확인용으로 둔다. 새 과제마다 별도 예약을 늘리지 않는다. 기본 운영 주기나 임시 종료일을 바꾸려면 과제 배정 변경과 구분해 현재 사용자 권한·지원 도구·설정 read-back을 적용한다.
5. **원장과 이력을 한 변경으로 맞춘다.** 일정표의 실행 순서·과제별 예정, 영향받은 일감의 priority/schedule/record_version·next_action을 실제 판단에 맞게 갱신한다. 변경 전후 순서·시각·근거·미룬 작업·담당·재개/검토 시각·인계는 기존 실행 기록에 남기고 일감의 schedule.replan_reference로 연결한다. 실제 일정 변경이 없으면 가짜 재배정 이력을 만들지 않는다. 자동 분산 잠금·완전한 일정 동기화가 구현됐다는 뜻은 아니다.
6. **장기 지연을 다시 본다.** 같은 등급·조건이면 먼저 접수된 일을 기본으로 하며, 반복 순연 또는 하루 이상 지연된 과제는 다음 오전 계획 점검(임시5회에서는07시, 기본3회 복귀 뒤에는11시)에서 영향·사용자 우선순위·의존성을 재평가한다. 검증·편집/실기기 근거를 생략해 밀린 일을 닫지 않는다. 필요한 새 근거가 없으면 이유와 다음 검토 시각을 유지한다. 중요한 순서 변경·큰 지연·필요한 결정은 짧게 알리고, 변화 없는 점검을 반복 통지하지 않는다.

## 충돌·회귀·일정 지연 관리

1. **제품 구현은 한 과제씩**, 읽기 조사·서로 다른 입력의 독립 검증은 병렬로 진행한다. 같은 파일은 소유자를 정해 한 작업자가 수정한다. 각 회차는 직전 실행·실제 진행 파일·원격 main·공개 판본을 먼저 확인한다.
2. 진행 중 작업은 일감 ID·현재 단계·수정 파일 범위·기준 커밋·브랜치/작업 사본·재개 지점·다음 예정 시각을 기존 실행 기록에 남긴다. 날짜나 오래된 상태만 보고 다른 작업의 파일·잠금을 없애지 않는다. 이 표 자체가 분산 잠금은 아니다.
3. **통합·배포는 기존 단일 경로 하나**다. 오래된 site 전체를 덮지 않고 최신 동시 게시물과 검수 입력을 보존한다. 후보의 ID·URL·PDF/필기 연결·정확한 전후 해시·영향 범위 회귀를 확인하고 기존 CI의 직렬화·stale revision 차단·복구 사본·공개 HTTPS 확인을 사용한다. 일반 게시에 새 승인자를 추가하지 않는다.
4. 검사 미완료·회귀·공개 영향이 남으면 그 후보를 배포하지 않는다. 선행 과제를 이어가며 후속 제품 구현의 날짜를 조정한다. 편집 판단·실기기 근거·접근권한이 없어 막힌 항목은 이유·필요 근거·다음 검토일을 기록하고 독립 가능한 과제로 이동한다.
5. 예정일 변경은 이 표와 해당 일감의 schedule 필드를 같은 변경에서 갱신한다. 예정/실제 착수/검증/배포/관찰을 구분하고, 누락 회차는 마지막 성공 이후 새 기록을 한 번에 확인한다. 지나간 회차를 수행한 것으로 만들지 않는다.
6. 중대한 장애·노출·손실은 예정표보다 우선한다. 원인·수정·복구는 기존 정책과 일감/사고 기록에 연결한다. 편집부(AEDAUT)의 콘텐츠 일정·주제·일반 발행 권한은 이 표가 인수하지 않는다.
