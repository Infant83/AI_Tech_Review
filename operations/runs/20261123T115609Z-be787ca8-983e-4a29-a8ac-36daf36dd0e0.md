reader_catalog_freshness implements revalidation with a validated cached fallback; l014_browser_recovery independently tests a real warm HTTP cache; root integrates the module version, source preservation and release. No other schedule or priority was displaced. Personal notes, storage, accounts, permissions, PDFs and authoring/mail automation are preserved. This is technical support for an authorized publication, not a new content workflow or approval gate.

Independent real HTTP-cache verification found that a503/no-store response can evict the prior valid cache before a force-cache retry. The first prototype is therefore not released. A cache-only validated snapshot captured before revalidation will remain in memory for that startup attempt; no personal storage or cache clearing is added. This failure and the corrected acceptance test remain part of the technical record.

The revised implementation captures an optional same-origin cache-only snapshot before revalidation, validates it, and keeps it only in startup memory. Fresh server content remains authoritative. It falls back to the snapshot after an error; unsupported/cache-miss browsers retain a bounded best-effort retry. All222 reader tests including14 new cases pass, with an independent integrator rerun. The earlier217-test prototype and its503 failure are historical evidence, not final success.

Final independent Firefox158 fixture validation passed on the same HTTP cache, origin and profile: old13-unit cache -> authoritative new14-unit response; then a503/no-store response with only one failed network request. The reader still opens the same16-page PDF at page2 with the exact existing one mouse-ink stroke. No account, cloud write, personal-storage clearing or physical Pencil trial was performed.
