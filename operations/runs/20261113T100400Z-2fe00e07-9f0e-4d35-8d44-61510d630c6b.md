## 저장소 준비 계약의 최소 후속 범위

독립 코드 감수에서 현재 `serveMedia`의 일치 ETag 응답이 객체 조회보다 먼저304를 반환함을 확인했다. 통합 담당도 실제 함수를 합성 누락 객체3상황으로 호출해 일반 GET503/no-store·store조회1회, 일치 ETag GET/HEAD304·store조회0회를 확인했다. 첫 격리 스크립트는 import 경로 오류로 실행 전 종료됐고 경로를 바로잡은 뒤 확인했다. 운영 코드나 실제 PDF를 바꾼 시험이 아니다. 304의 본문 없음 자체를 SHA 실패로 해석하지 않으며, 누락 객체를 조건부 성공으로 가리지 않는 활성화 전 계약 항목이다.

후보에서는 선택한 객체의 존재·크기를 확인한 뒤304를 판단하도록 준비한다. head의 크기 확인은 SHA 증명이 아니므로 같은 길이 오객체는 전체 업로드 검증·원격 봉인에서 확인한다. 추가 조회 수·비용과 매 Range 전체 해시의 부하도 구분한다. 기대 SHA를 무시하는 현재 v1 준비 Worker는 새 카탈로그의 안전한 되돌림 대상이 될 수 없으므로 최초 활성화부터 지원 판본을 보존한 전달 코드·매핑을 사용하도록 [기존 계약](../../SITE_OPERATIONS.md#공개-pdf-저장소-이전)을 보완했다.

첫 로컬 후보 범위는 `public_media.py`·`serve.mjs`와 기존 Python/JS 검사2파일이다. 경로별 현재/허용 구판SHA→불변key, 검증한 이전 export 병합, 판본을 먼저 선택하는 GET/HEAD/304/실제 부분 Range/If-Range, 잘못된/중복/다른 글 query 거절, 실제 fallback spy와 구신 공존·되돌림 검사를 다룬다. `worker.mjs` 어댑터는 실제 필요할 때 범위를 다시 기록한다. 원격 업로드/재시도·전체해시·코드/매핑/설정/Pages 결속 봉인과 원격 실제 복원·공통 릴리스 검사·정적 제외는 뒤 단계이며 이번 후보의 완료 범위가 아니다. 공유 리더의 전체 bytes SHA 확인이 raw PDF 링크나 서버의304/Range 계약까지 보증하지 않는 점도 유지한다.

기존 공급자 인계 화면은19시에도 정상 로그인/암호 입력이 필요했다. 앞선 CLI 거절 뒤 실제 계정/R2 연결 복원·버킷·사용량·청구를 확인한 새 근거는 없다. 같은 막힌 경로를 재시도하거나 새 권한/과금/라우트/업로드를 만들지 않았으며 기존 인계 탭만 유지했다. 준비 코드 계약을 현재 공개 장애로 과장하거나 실제 저장량을 절감했다고 기록하지 않는다.
