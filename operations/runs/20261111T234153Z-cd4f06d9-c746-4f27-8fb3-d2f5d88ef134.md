## 판단과 적용

사용자는 새 요청·급박한 과제가 들어오면 우선순위·운영순서를 재조정하고 그 순서에 따라 작업 슬롯을 배정·변경하도록 지시했다. [일정표](../SCHEDULE.md)에 접수/회차 시작의 재판정, 현재 제품 실행 순서, 안전한 중단과 인계, 구현·독립 검증·통합 슬롯의 동반 조정, 밀린 과제 재개/검토 시각, 장기 지연 재평가 절차를 넣었다. 기존 개발 운영 정책·운영 기록 안내·실행 양식도 같은 절차를 참조한다.

최신 사용자의 구체적인 우선순위 지시를 우선하고, 지정하지 않은 부분은 영향·시급성·근거·의존·수정/중단 위험·대기 기간으로 판단한다. P0는 발견한 실행에서 우선 확인·허용된 완화를 진행하고 P1은 가장 빠른 안전한 슬롯으로 앞당긴다. 큰 영향의 미확인 제보는 확인을 미루지 않되 실제 장애/노출 확정과 구분한다. 같은 조건의 동급 과제는 먼저 접수된 일을 기본으로 하며 대기 기간만으로 장애 등급을 자동 상승시키지 않는다.

긴급 확인이 정해진11시 구현/19시 통합 역할이나 이전 과제의 모든 검사 완료를 기다리지 않게 했다. 진행 상태·파일 범위·기준 커밋·후보/검증 상태·재개 지점을 보존하고 기존 단일 배포 경로를 유지한다. 이미 진행 중인 배포는 실제 단계와 공개본·구판/중복 알림 영향을 확인하며 무조건 취소·재실행하지 않는다.

실제로 재배정할 때에는 일정표·해당 일감의 priority/schedule/다음 행동을 함께 갱신한다. 변경 전후·이유·담당·미룬 작업과 다음 재개/검토 시각·인계는 기존 실행 기록을 사용하고 해당 일감의 schedule.replan_reference에 연결한다. 반복 순연/하루 이상 지연된 과제는 다음 오전 계획 점검에서 다시 본다. 기본3회 복귀 뒤에는07시 대신11시를 사용한다.

## 실제 설정과 보존

같은 ai-tech-review 예약의 프롬프트에 현재 실행 큐와 새 재배정 절차를 반영했다. 기존 날짜 순서는 초기 기준이며 최신 일정표의 재조정 순서를 따른다고 명시했다. 지원 도구가 update/ACTIVE 성공을 반환했고, 실제 저장 read-back에서 prompt·updated_at만 달랐다. 기존5회 시간 규칙·임시 종료/기본 복귀 조건·식별자·종류·이름·대상·ACTIVE·created_at은 보존됐다.

이번 요청은 운영 규칙 정비다. 실제 긴급 사건이나 특정 새 제품 요청이 접수된 것으로 만들지 않았고, 현재 네 제품 과제의 priority·예정일·순서는 그대로다. 재배정 규칙을 기록한 것을 실제 슬롯 이동 이력으로 꾸미지 않았다. 제품 코드·출판 입력·PDF·필기·구독·DB·편집부(AEDAUT)의 콘텐츠 예약/발행 권한도 바꾸지 않았다.

상주 실시간 감지·새 자동 기동·분산 잠금·소프트웨어 일정 엔진을 구현했다고 표현하지 않는다. 기존 회차와 진행 중 대화에서 확인한 요청을 운영팀이 기록·인계·재배정하는 방식이다. 일반 게시에 추가 승인자를 두거나 긴급이라는 이유로 기존 권한·검증·복구 경계를 생략하지 않는다.

## 검증과 다음 행동

독립 읽기 감수에서 P0/P1 전환 예외·큰 영향 제보의 우선 확인·현재 작업 보존·후속 검증/통합 전파·동급 순서·장기 지연·실기기/편집 판단 의존·기본 주기 복귀의 정합성을 확인했다. 사용자 명시 순서 우선과 실행 참조 필드를 명확히 하라는 권고를 반영했다. 문서·JSON·링크·기존 과제 시각/상태·diff와 다른 작업의 미추적 인계 해시 보존을 확인했다. 문서/프롬프트 변경이므로 제품 테스트 반복·후보 생성·사이트 배포·실제 롤백은 하지 않는다.

다음 회차는 현재11/12 11시 갱신시각 수정 배정을 유지하되, 그 전에 들어온 최신 요청·발견과 실제 진행 상태를 먼저 확인해 필요 시 이 절차로 재배정한다. 실제 중요한 순서 변경·큰 지연·필요한 결정은 짧게 알리고 정상 점검을 반복 통지하지 않는다.
