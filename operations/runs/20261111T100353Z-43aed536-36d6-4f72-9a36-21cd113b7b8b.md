## 사용자 확인과 조사 범위

사용자는 오늘뿐 아니라 이전 글에서도 알림이 없었고 iPhone 홈 화면에 추가한 앱을 사용한다고 확인했다. 새 테스트 없이 최근 수신 목록을 확인한 결과, 글 기록이 있지만 배너는 없었다고 답했다. 이는 기록된 글이 SW 수신·기기 내 저장 단계까지 도달한 근거다. 모든 과거 글의 수신, 표시 요청 성공 또는 실제 OS 배너를 직접 확인한 것으로 확대하지 않는다. iOS 버전과 정확한 글·수신 시각은 아직 미확인이다.

오늘 확인한 기존 글 개정의 푸시 미생성은 [직전 조사](20261111T093848Z-402dc3d2-c189-4d77-ad6e-7e1f82d5452a.md)에서 따로 확인했다. 이 정책만으로 이전 신규 게시물의 표시 제보를 설명하지 않는다. 현재 iPhone 알림 설정의 배너·즉시 전달/요약 상태를 확인 요청했으며, 원인을 집중 모드·권한으로 단정하거나 구독을 초기화하지 않았다.

## 코드 감사와 최소 보완

기존 SW는 push 처리 초기에 `showNotification()`을 시작하며 IDB·배지 처리와 독립 실행한다. 포커스가 있다고 표시 호출을 생략하지 않고, 새 글의 이벤트 tag도 서로 다르다. 현재 수신 목록에는 표시 Promise의 성공·실패가 저장되지 않는다. 독립 임시 VM에서는 표시 Promise가 즉시 거절되면 `Promise.all`의 전체 대기가 로컬 기록 완료보다 먼저 거절되는 진단 공백을 재현했다. 이것이 실제 아이폰 문제의 원인이라고 확정하지 않으며 이번에 SW나 로컬 기록 형식은 바꾸지 않았다.

[WebKit 형식·호환성 설명](https://webkit.org/blog/16535/meet-declarative-web-push/)과 [Safari18.4 지원 안내](https://webkit.org/blog/16574/webkit-features-in-safari-18-4/)를 독립 대조했다. 지원되는 iOS/iPadOS18.4+ 홈 화면 앱은 선언형 설명이 있으면 SW가 표시하지 못한 경우 브라우저가 fallback을 표시할 수 있다.

기존 flat `title/body/url/articleId/tag`를 모두 유지하고 `web_push:8030`과 같은 제목·본문·이동 URL·tag·기존 아이콘의 `notification` 설명만 추가했다. 구형 브라우저·SW 경로를 유지하고 기존 구독·키·scope를 바꾸지 않는다. 실제 기기 배지 수를 서버가 알 수 없으므로 `app_badge`를 추가하지 않았으며 `silent/renotify` 정책도 바꾸지 않았다. 전송 대상·이벤트 생성·TTL·Topic·high 우선순위·암호화·큐·재시도·DB 스키마는 그대로다.

## 격리·독립 검증

- 새 선언형 전송 회귀는 수정 전 필드 부재로 실패했고 수정 후 통과했다. `npm run check`와 backend 전체59개 검사가 모두 통과했다.
- 실제 새 글·본인 요청 테스트 전송 경로를 격리 transport로 받아 독립 `http_ece` 복호화 후 flat/nested 일치·제목/URL/tag·헤더 보존과 민감 필드 비노출을 확인했다. 외부 푸시는 없다.
- 최대 허용240자·720B 다국어 제목,180자 리뷰 ID와 PDF 렉처 경로도 원문 손실 없이 plaintext≤3000B·암호문<4096B였다.
- 독립 VM에서 기존·hybrid 리뷰/렉처/테스트가 push당 표시 호출1회, 원 URL/tag/icon, 기존 글 ID·최근 목록·배지·중복 제거를 유지했다. 테스트 알림은 기존처럼 최근 글 목록·배지를 늘리지 않았다.
- 독립 코드·공식 형식 감수와 diff 검사를 통과했다. VM 검증은 native fallback·실제 iPhone 배너·native/JS 중복 표시를 검증한 것이 아니다.

## 기존 Worker 배포와 보존 확인

기존 공급자 연결과 활성 버전을 읽고 전후 비교 자료를 비공개 로컬 경로에만 보관했다. `wrangler4.159.0` dry-run 통과 후 `--keep-vars --strict --autoconfig=false`로 기존 Worker에 소스를 배포했다. 활성100%·소스 태그 `adopt-declarative-21ee3e502849`를 재조회했고, binding 메타데이터·runtime·handlers·공개 VAPID 설정이 동일함을 확인했다. 비밀값은 읽거나 출력하지 않았고 새 자원·권한·키·마이그레이션을 만들지 않았다.

10:01:25UTC 확인에서 공개 설정은 HTTPS200·pushEnabledtrue, 익명 `/v1/study/me`는200·account:null, 익명 노트는401이었다. 정적 공개본은 기존 `ab575a676113f44d7ca3cc0bf7997a823f7a7412`로 유지된다. 배포 전후 D1 SELECT 집계는 구독3·이벤트21·배송45건 sent/최대시도1로 동일했다. 서버 집계를 실제 단말 표시의 증거로 사용하지 않는다.

독립 담당도 전후 배포 영수증·활성100%·리소스/집계를 대조하고 직접 HTTPS 설정200·익명 계정200/null·노트401 및10:06:36UTC 정적ab575a6 유지를 확인했다. 공용 기록의 범위·개인정보 감수도 통과했다.

정적 Pages 재배포·새 글·임의 테스트·과거 재발송·구독/DB 변경은 없었다. 회귀가 확인되면 공급자의 직전 Worker 코드 버전으로만 복구하고 기존 high 전송·구독·키·자료를 유지할 수 있다. 실제 롤백이나 DB 복원은 하지 않았다.

## 남은 확인과 인계

원래 미수신 원인과 이번 보완의 실기기 효과는 미확인이다. 서버 수락·SW 수신·표시 요청 결과·실제 배너를 분리한다. 사용자 설정과 기록된 글의 수신 시각을 대조하고, 필요한 경우 표시 요청 결과를 기기 안에만 남기는 최소 진단을 후속 검토한다. 원격 ACK나 개인정보 전송을 새로 추가하지 않는다.

native fallback으로만 표시된 건은 JS가 실행되지 않아 최근 수신 기록이나 배지가 갱신되지 않을 수 있다. 목록 부재를 미도착의 확정 증거로 삼지 않으며 실제 OS의 요약·집중 모드·표시 정책을 우회하거나 도착을 보장한다고 설명하지 않는다. 기존 글 개정·브리핑의 발송 범위는 별도 정책으로 유지하고 단순 재배포마다 알림을 만들지 않는다. 일감은 `in_progress`로 유지한다.
