# 관리 쓰기 API의 첫 계약과 구현 순서

- 관련 일감: `OPS-4b849a94-be8d-4cf0-a73e-d12a21104824`
- 기준: 2026-11-20, 소스403d920·실제 공개20b650e. 읽기 v1은13c7991로 통합됐다.
- 상태: 11/20 기술 계약 감수 뒤11/21 A의 정식 독립 감수·읽기근거 결속 보완·로컬 도구 통합265b9a2를 마쳤다. 아래 B–E·HTTP/인가·실제 저장/발행은 후속 목표이며 현재 운영 API가 아니다.
- 역할: 운영팀(ADOPT)은 도구·권한/충돌/복구를 구현하고 편집부(AEDAUT)는 수정할 문구와 발행을 판단한다. 기존 일반 게시의 권한·검증·단일 경로를 유지한다.

## 첫 범위

첫 수정 대상은 **이미 등록한 리뷰 한 건의 `subtitle`, `category`, `tags`, `summary`**다. [기존 허브 필드 정의](../../scripts/publication_intent.py)와 [게시 절차](../../PUBLICATION_WORKFLOW.md)의 범위를 그대로 사용한다. 제목·ID·원 발행일·URL·번역·본문·그림·PDF, archive import/교체/삭제는 후속 범위다. 실제 문구를 기술 구현 과정에서 자율 작성하거나 기존 자료를 일괄 변환하지 않는다.

우선 서버·DB·자격 변경 없이 로컬 요청 사전검사 core를 만든다. 그 뒤 독립 checkout의 변경 저장과 복구, 기존 후보 생성, 서버 인가, 얇은 HTTP/API·화면, 실제 발행 연결 순서로 확장한다. 읽기 v1과 첫 사전검사기의 성공을 저장·게시 성공으로 표시하지 않는다. Worker가 로컬 Python/Git을 직접 실행할 수 있다고 가정하지 않는다.

## 현재 권한과 후속 인가

| 현재 경로 | 실제 권한과 연결할 때의 경계 |
| --- | --- |
| 개인 study 계정·owner/editor | 개인 자료·초안·필기 권한이다. 공개 등록 편집 권한이 아니다. |
| study reviewer | 승인도 `published:false`, `editorialExportRequired:true`다. 공개 편집 capability로 자동 승격하지 않는다. |
| publisher Bearer | [worker.js](../../.automation/cloudflare/reader-engagement/src/worker.js)의 카탈로그 검증·DB/outbox/queue 동기화 자격이다. Git/원고 편집 자격이 아니며 관리 브라우저에 전달하지 않는다. |
| Pages CI | 기본 `contents:read`, 배포 job만 Pages/id-token 권한을 가진다. 원고를 Git에 쓰는 서버 자격이 현재 준비됐다는 뜻이 아니다. |
| 현재 로컬 운영자 | 기존 요청 권한으로 CLI·독립 작업 사본을 다룬다. 이 연결을 공개 HTTP 이용자의 권한으로 전이하지 않는다. |

후속 서버는 인증한 주체의 대상·동작별 capability를 **서버에서** 확인한다. 익명/일반 독자/개인 reviewer는 거절하고, 편집·기술 실행 권한과 작업 소유권을 구분한다. 요청 payload의 actor/role·CORS·숨긴 버튼은 인가 근거가 아니다. 기계 자격도 주체와 범위가 식별돼야 한다. 재조회·동일 요청 replay에서도 인가를 다시 확인하며 다른 주체의 작업/멱등 키를 읽어주지 않는다.

실제 서버의 실행 호스트·Git 자격·권한/세션 구조와 보존·복구는 후속 구현 전 구체화한다. 기존 연결을 재사용할 수 있는지 확인하고, 새 인증 구조·권한 확대가 필요한 실제 활성화는 정책의 결정 경계를 적용한다. 이번 계약에서 계정/역할 부여·새 공급자/서비스·유료 계약·Worker/D1 배포는 하지 않는다. 이 후속 결정을 일반 게시의 추가 승인 조건으로 만들지 않는다.

## 요청과 버전 결속

논리 작업명은 `review_hub_metadata_update`, schemaVersion은1이다. HTTP 주소는 아직 배정하지 않는다. 로컬 입력과 후속 API가 같은 core를 사용한다.

| 필드 | 첫 사전검사의 요구 |
| --- | --- |
| `operation`, `schemaVersion` | 위 작업/판본만 허용한다. 알 수 없는 필드·JSON 중복 key·상수·잘못된 UTF-8을 거절한다. |
| `sourceId` | native 리뷰 folder ID다. 전체 등록 reader에서 실제 리뷰를 찾고 경로는 서버/로컬 core가 정한다. 관리 행의 `review:` 접두어·임의 경로/명령/URL은 받지 않는다. |
| `expectedSourceRevision` | 호출자가 확인한40자리 소스 commit. 실제 현재 source와 다르면 조용히 덮지 않는다. 공개 release revision과 별도다. skip-ci 기록 commit 차이를 미게시로 해석하지 않는다. |
| `expectedInputs` | [review_inputs](../../scripts/publication_intent.py)의 전체 등록 SHA·출판 원본 SHA·보호 등록 SHA를 모두 결속한다. 하나라도 없거나 다르면 쓰지 않는다. |
| `expectedReleaseRevision` | 확인한 완전한 release/catalog/updates 묶음의 공개 source revision. 새 정상 게시가 있으면 최신 묶음을 다시 인수한다. |
| `expectedReleaseEvidence` | 확인한 release/catalog/updates **각 원시 bytes의 SHA-256 세 개**다. 제공한 완전한 묶음을 기존 validator로 검증하고 세 값을 다시 계산해 비교한다. 같은 source revision의 다른 재빌드/갱신 묶음도 `release_changed`로 거절한다. revision이나 snapshot 하나의 hash만으로 대신하지 않는다. |
| `patch` | 위 네 필드 중1개 이상이다. 삭제/null·다른 필드·중첩 경로/명령을 거절한다. 병합한 등록 전체를 기존 strict reader로 다시 검증한다. |
| `idempotencyKey` | 요청별 UUID. 후속 지속 저장 단계에서 인증 주체·작업 범위·정규화한 전체 요청 hash에 결속한다. 사전검사기는 키/요청 fingerprint만 검사하며 지속 멱등성을 구현했다고 표시하지 않는다. |

첫 입력은 UTF-8 JSON32,000B 이내로 제한한다. 변경 문자열은 subtitle1,000/category200/summary8,000 Unicode 문자, tags40개·각200문자 이내이며 기존 single-line 검증도 적용한다. 한도를 넘으면 자르지 않고 거절한다. 경로/태그/본문을 명령으로 실행하지 않는다. 원본·입력의 심볼릭 링크, 읽는 동안의 파일/등록 집합 변경과 검증 실패도 명시적 reason code로 중단한다. native 등록/원본 해시는 제어된 입력에서 다시 계산하고 클라이언트가 보낸 값만 신뢰하지 않는다.

읽기 v1의 `snapshotToken`은 읽은 묶음 식별자이며 쓰기 인가·잠금·유일한 CAS 토큰으로 쓰지 않는다. 첫 사전검사는 현재 v2 지속 요청의 원본/보호 등록 결속이 확인된 리뷰만 받는다. v1·검토 입력 없음·옛 선언 결속 부족을 임의로 보충하거나 `--review`로 우회하지 않고 기존 재검증 필요 상태로 반환한다. 이는 첫 core의 제한이며 모든 일반 게시의 새 감수 조건이 아니다.

A의 공개 출력 결속은 주 웹 HTML과 등록된 번역 HTML의 선언된 `after`가 확인한 baseline의 내용 SHA와 일치하는지 검사한다. 나머지 reference도 선언이 있으면 대조하지만, 변경되지 않은 그림·첨부에 새 변경 선언을 요구하지 않는다. 전체 reference의 선언을 요구하던 첫 후보 조건은 실제 공개 v2 대상 전부를 제외하므로11/20 초기 대조에서 바로잡았다. 이는 HTML 결속과 v2 전체 출판 입력의 확인이며 모든 공개 첨부의 실제 bytes 보존을 검증한 것은 아니다. 전체 파일 보존은 C의 후보·연속성 검증에서 확인하고, A 구현은11/21 11시 정식 독립 감수·로컬 도구 통합을 마쳤다.

요청 fingerprint는 검증한 operation/schema·sourceId·source/target/release 근거와 patch를 정렬 key·고정 구분자의 UTF-8 JSON으로 직렬화해 계산한다. idempotencyKey·인증 자격·확인 시각은 제외하고 인증 주체는 후속 멱등 저장 key에 별도로 결속한다. 문구를 정규화/잘라서 다른 patch를 같은 요청으로 만들지 않는다. 공개 묶음은 [기존 수집기](../../scripts/publication_release.py)의 같은 source 재빌드 방어와 원시 bytes 결속을 재사용한다.

A의 소스 root와 이미 취득·검증한 로컬 공개 묶음 경로는 운영자가 별도로 지정하며 요청 JSON에서 임의 경로/URL·원시 가짜 묶음을 받아 취득하지 않는다. 해시 일치는 인가나 실제 최신 공개 열람의 증명이 아니다. 후속 서버/통합은 제어된 기존 공개 취득 경로에서 최신 완전 묶음을 확인해 다시 비교해야 한다.

## 충돌·재시도·실패 계약

현재 checkout의 advisory lock은 협력 프로세스의 로컬 직렬화다. [publication_lock.py](../../scripts/publication_lock.py)를 분산 잠금으로 표시하지 않는다. 후속 변경 저장은 요청마다 독립 checkout에서 실행하고, 시작/종료의 입력 재대조와 **실제 Git ref 갱신 시점의 expected old SHA 비교**를 모두 적용한다. 등록 변경이 없어도 remote main이 전진하면 첫 구현은 충돌로 중단하고 새 기준·새 요청으로 재검증한다. 자동 재기준화로 검토한 내용을 바꾸거나 동시 게시물을 덮지 않는다.

| 상황 | 후속 동작/응답 의미 |
| --- | --- |
| 형식/한도/보호 필드/대상 오류 | `invalid_request` 또는 `unsupported_scope`로 거절, HTTP adapter에서는400/422. 원본·작업 queue·알림을 바꾸지 않는다. |
| 현재 값과 같은 patch | `no_change`와 확인한 입력 근거를 반환한다. 새 commit·후보·배포·알림을 만들지 않는다. |
| 인증/인가/다른 주체의 작업 | 401/403 또는 비공개 작업의 존재를 노출하지 않는 응답. 재시도 키도 인가를 대신하지 않는다. |
| 원본/등록/공개 기준 변경 | 409 `source_conflict`/`input_conflict`/`release_changed`. 새 기준 인수 뒤 새 요청을 만든다. |
| 같은 주체·키·정규 요청 | 저장 단계가 구현된 뒤 같은 작업 ID/현재 단계를 반환한다. 재빌드·다시 commit·직접 알림을 만들지 않는다. |
| 같은 키·다른 내용/기준 | 409 `idempotency_conflict`. 기존 요청을 바꾸지 않는다. |
| Git 저장 뒤 응답/작업 DB 실패 | `outcome_unknown`으로 두고 정확한 operation ID·commit·변경 hash를 대조한 뒤 재개한다. 확인 없이 새 commit을 만들지 않는다. |
| 입력 검증·후보 생성 실패 | 독립 작업만 실패 처리한다. 공개본은 보존하며 실패 사유는 값/절대경로 없는 코드로 기록한다. |
| main push 뒤 더 최신 게시가 앞섬 | 기존 stale guard를 재사용해 `superseded_not_deployed`로 구분한다. 낡은 소스를 재배포하지 않으며 현재 공개본/정확한 변경 포함 여부를 별도로 대조한다. |
| 배포 성공·복구/동기화 실패 | `deployed_followup_incomplete`. 실패한 후속 단계와 현재 source를 확인해 재개한다. 배포 성공을 지우거나 전체 구판을 무조건 재실행하지 않는다. |

Git은 원본·등록·지속 요청의 단일 원장이다. 후속 작업 DB/저널에는 소유·상태·멱등 hash·commit/검증 참조를 두고 또 다른 편집 정본을 만들지 않는다. commit에 안전한 operation ID를 결속해 Git 성공/응답 실패를 조정할 수 있어야 한다. 작업 저장과 ref 갱신은 원자적이라고 가정하지 않는다. 키 보존·중단 후 조정·작업 회수 조건과 동시 요청의 유일성은 지속 저장 구현 때 검사하고, 기록 소실/만료를 동일 요청을 다시 실행할 허가로 쓰지 않는다.

## 기존 게시 경로 연결

[prepare_candidate](../../scripts/prepare_publication.py)는 순수 읽기 함수가 아니다. 성공 시 원본 checkout의 `publication/requests`와 선택된 변경 선언도 쓸 수 있다. HTTP handler가 공유 checkout에서 바로 호출하지 않는다. 독립 작업 사본의 허용 delta와 대상 밖 불변을 검증하고 실제 이전 배포 묶음을 인수한 뒤 기존 후보·연속성·페이로드·변경 동선 감수를 적용한다. 새 후보를 보호하기 전에 미리보기 서버를 열지 않는다.

첫 네 필드 변경은 기사 HTML/PDF·ID/주소/원 발행일·필기·기존 알림 ID를 보존해야 한다. 후보 생성기가 대상 밖의 정상 지속 요청도 갱신하면 자동으로 광범위한 쓰기를 허용하지 않고 해당 diff를 보고 중단한다. 기존 publisher의 정상 재생/선언 결속을 수작업 hash 치환으로 우회하지 않는다.

확정된 source SHA를 [기존 Pages workflow](../../.github/workflows/pages.yml)에 전달해 하나의 봉인된 아티팩트로 배포한다. 같은 작업의 상태는 `validated`·`staged`·`candidate_verified`·`source_integrated`·`deployed`·`https_verified`와 recovery/notify 결과를 구분한다. 최종 성공은 실제 공개 source·대상 변경 hash와 필요한 HTTPS, 네 작업/후속 상태를 확인한 뒤다. 로컬 저장이나 job HTTP202만으로 `published:true`를 반환하지 않는다.

독자 동기화는 기존 실제 공개 feed 검증·revision replay·outbox/event 중복 방지를 재사용한다. 같은 기존 ID의 메타데이터 변경을 새 글로 발송하지 않는다. 재시도 중 기존 outbox를 복구할 수 있으므로 무조건 queue0/정확히1회 단말 수신을 보증하지 않는다. 관찰자가 검증용 푸시를 보내지 않는다. 공개 정적 복구 사본과 개인 D1/필기 복구는 별도다.

## 세 자료의 권위를 나눈다

| 자료 | 권위와 보존 |
| --- | --- |
| Git source/candidate tree | 원본 등록과 실제 후보 내용의 정본. 변경 값의 mutable 복사본을 journal에서 따로 편집하지 않는다. |
| 불변 key claim | repository identity·local principal scope·operation·idempotency key hash의 사용 이력. fingerprint·operation ID·기준 SHA·대상만 보존하고 원고/문구·자격정보를 넣지 않는다. 작업 시작 전에 배타적 생성·fsync로 예약하며 자동 덮어쓰기/만료/삭제하지 않는다. |
| Git operation receipt와 journal 상태 | 결정적 operation ref/commit metadata는 실제 저장 결과의 근거다. journal의 진행 상태는 그 근거를 가리키는 재생성 가능한 표시다. journal만 보고 Git 저장 성공을 만들지 않는다. |

요청 값은 caller가 다시 제공한다. 중단 후 같은 요청의 fingerprint를 재확인해 이어가므로 journal이 또 다른 원고 정본이나 임의 편집 DB가 되지 않는다. key claim과 결과 Git ref는 같은 내용의 두 정본이 아니라 각각 키 예약과 실제 저장 결과를 증명한다. 둘은 원자적 트랜잭션이 아니므로 불일치를 숨기지 않고 조정한다.

operation ID는 repo identity + local principal + 고정 operation scope + key에서 안정적으로 정한다. 대상/patch/세 기준은 fingerprint에 포함한다. scope에 target을 넣어 다른 target의 같은 키를 별도 작업으로 우회시키지 않는다. commit metadata에는 operation ID·fingerprint·기준 parent/source SHA·대상 경로/등록 before/after SHA·phase를 결속한다. operation ID 문자열 하나만 같다는 이유로 결과를 인수하지 않는다.

개별 상태뿐 아니라 사용된 key 자체가 사라지는 경우도 다룬다. 한 store의 key inventory에는 key hash·불변 claim hash만 보존하고, 개별 claim/operation ref와 대조한다. 새 key를 먼저 inventory에 예약·fsync한 뒤 claim/receipt를 만들며, 그 사이 중단으로 예약만 남으면 `outcome_unknown`으로 정지한다. inventory에 있는 key의 claim과 receipt가 사라져도 신규 key로 재실행하지 않는다. inventory·claim·Git 결과의 다중 파일 처리를 원자적이라고 주장하지 않고 각 경계 실패를 fixture에 넣는다. 전체 보존 근거를 함께 잃는 한계는 아래와 같이 별도로 남긴다.

## 최소 처리와 실제 ref CAS

1. 요청 bytes를 한 번 받아 parser를 적용하고 immutable 요청 객체를 유지한다. 새 요청에는 A를 재실행하고 반환 fingerprint/세 기준이 보관한 요청과 같은지 확인한다. A의 성공 보고서를 저장 인가나 원자적 snapshot으로 쓰지 않는다. 수정할 원본 등록도 검증한 Git commit/blob에서 읽고 raw SHA를 A의 checked registration SHA와 대조해, B에서 별도 읽은 문구를 섞지 않는다.
2. trusted-local principal/operation/key로 기존 claim·receipt를 먼저 조회한다. 기존 작업의 replay는 현재 A 입력이 바뀌었다는 이유로 새 작업을 만들지 않고, 원래 결과/현재 단계와 별도 stale 상태를 돌려준다. 주체별 실제 재인가는 D의 후속 계약이다.
3. 새 key만 로컬 영속 claim으로 예약한다. 동일 store의 협력 프로세스는 보존하는 inode의 advisory lock으로 직렬화한다. 이것은 분산 잠금이 아니다. 같은 key/다른 fingerprint는 `idempotency_conflict`다. A의 `no_change`는 이 시점에 그 결과의 불변 tombstone만 남기고 끝내며 다음 Git 처리로 가지 않는다.
4. 실제 sandbox Git에 operation receipt ref를 배타적으로 만든다. 이 단계에서 기사 tree를 바꾸지 않는 claim receipt를 남겨, 이후 journal 상태가 없어도 사용된 key를 찾을 수 있게 한다.
5. 고정한 Git 등록 객체에 허용 patch를 병합하고 native validator를 적용한다. 후보의 base 대비 tree diff는 그 등록 파일 하나와 예상 before/after bytes여야 한다. operation metadata는 commit metadata/전용 ref에 두고 공개 tree에 내부 journal을 추가하지 않는다.
6. **같은 local Git ref transaction 안에서** sandbox main의 expected source SHA를 verify하고 operation result ref를 expected old claim SHA에서 candidate SHA로 갱신한다. 시작 전 HEAD 읽기만으로 대신하지 않는다. 구현 시 local Git의 verify+expected-old update 동작을 실제 fixture로 확인한다. 원본 main이나 원격 ref의 CAS를 구현했다고 보고하지 않는다.
7. ref 성공 뒤 journal 상태를 기록한다. journal 실패/응답 유실이면 `outcome_unknown`이며, 다음 조회에서 receipt commit의 fingerprint·base parent·변경 경로/등록 hash를 확인해 같은 candidate SHA로 조정한다. 새 commit/ref를 만들지 않는다.

새 key라도 patch가 현재와 같으면 `no_change`다. Git commit/ref·후보·빌드·배포·알림은 만들지 않으며, 키를 기록할 경우 그 결과도 명시적으로 로컬 no_change tombstone으로 보존한다. 같은 내용에 다른 key는 자동으로 같은 요청이라 추정하지 않는다. 최종 중복 발행·알림의 방지는 C/E까지 이어지는 별도 계약이다.

첫 B1은 key claim과 receipt의 자동 GC/만료/삭제를 구현하지 않는다. store가 이미 초기화됐는데 핵심 파일이 사라졌으면 신규 store처럼 재생성하지 않는다. 모든 보존 근거가 함께 사라진 경우 과거 작업이 없었다고 증명할 수 없으므로, 이 최초 범위가 전체 디스크 유실까지 감지/복구한다고 주장하지 않는다. key/store 보존·복구 사본·초기화 epoch의 원격 보존은 실제 운영 store 활성화 전 후속 조건이다.

**B1 종료는 위 로컬 저장·replay·충돌·중단 조정과 전후 불변을 독립 검증하고, 실제 command/범위/남은 실패를 다음 작업자가 재현할 수 있을 때다.** 저장 성공 한 번이나 journal 파일 생성만으로 B 완료라고 하지 않는다. C의 빌드·전체 첨부 연속성, 실제 원본/원격 통합 CAS, D의 서버 인가·지속 작업 호스트, E의 공개 확인·알림은 미완료로 남긴다.

## 주체와 권한의 범위

신뢰된 로컬 CLI로 한정할 수 있다. principal은 요청 JSON의 actor가 아니라 운영자가 통제하는 sandbox 설정에서 주며, 같은 OS 계정을 쓰는 에이전트를 암호학적으로 구분한 인가라고 주장하지 않는다. 첫 fixture에는 고정 local principal과 고정 허용 operation/target만 둔다. 사용자의 기존 개발·게시 권한은 유지하며 ADOPT를 새 게시 승인자로 만들지 않는다.

이번 작은 fixture 엔진에는 새 서비스·인증·과금 결정이 필요하지 않다. 실제 원본 ref/원격 연결·상시 호스트·Git 쓰기 자격이나 편집 account/capability를 활성화할 때는 구체적인 실행 주체·권한·복구를 먼저 제시하고 기존 정책의 결정 경계를 적용한다. 기존 권한으로 가능한 정상 CLI 게시에 다시 승인을 요구하는 규칙으로 확대하지 않는다. publisher Bearer나 개인 study reviewer 권한을 Git writer 자격으로 재사용하지 않는다.

## B1 착수·독립 검토 목표

- 오늘 **2026-11-21 19:00 KST**: A가 정식 PASS/통합된 경우만 B1의 위 bounded fixture 엔진 첫 후보 구현·목표 검사를 시작하는 슬롯으로 사용한다. 전체 B 완료/발행 활성화 시각이 아니다. A 미통과면 B는 미착수로 두고 A의 남은 감수·수정에 같은 슬롯을 쓴다.
- **2026-11-22 11:00 KST**: 첫 B1 후보의 독립 검토 목표. 실패/미완성 범위를 평가하며 시간만 됐다고 통합하지 않는다.
- 그 검토 뒤 **11/22 19:00 KST** 또는 다음 기존 슬롯에서 B1 수정/로컬 재개 범위와 B2(실제 원본의 읽기 연결·원격 없는 작업 사본/통합 경계)를 재선정한다. B2 이후의 구현/완료 납기는 지금 확정하지 않는다.

기존 주요 개발 슬롯에 채택한 하위 계획이며 새 예약·서비스·추가 상시 게이트를 만들지 않는다. 공용 상태와 다음 행동은 이 계약·기존 일감/일정표·실행 기록으로 이어간다.
