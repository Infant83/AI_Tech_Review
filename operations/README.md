# 개발 운영 기록

이곳은 에이전틱 운영팀(Agentic Operations Team, AOT)의 기술 일감과 지원 이력이다. [웹저널 조직과 역할](../JOURNAL_TEAM_CHARTER.md)에 따라 콘텐츠의 통찰·기획·집필·과학 감수·편집·발행 판단은 에이전틱 편집부(Agentic Editorial Room, AER)가 맡는다. 사용자 제보를 접수하면 먼저 기술 문제와 편집 과제를 구분한다. 순수한 콘텐츠 요청은 기존 편집 기록에 연결하고, 기술 지원이 필요한 부분만 이곳의 일감으로 다룬다.

[개발 운영 정책](../DEVELOPMENT_OPERATIONS_POLICY.md)과 [개발 계획](../DEVELOPMENT_ROADMAP.md)에 따라 피드백·개발 과제·검증·운영 관찰을 연결한다. 이 폴더의 기록은 대화가 바뀌어도 이어서 사용할 공용 업무 기억이다. 기록을 만들었다고 구현·예약 실행·배포가 완료되는 것은 아니다.

## 기록 위치

| 위치 | 용도 |
| --- | --- |
| `issues/OPS-<UUID>.json` | 일감 하나의 요약·판단·현재 상태·다음 행동 |
| `events/EVT-<UUID>.json` | 같은 일감에 여러 작업자가 남긴 추가 관찰·변경 제안 |
| `runs/<UTC 시각>-<UUID>.md` | 실행 한 번의 계획·실행·검증·인계 요약 |
| `decisions/DEC-<UUID>.md` | 여러 일감에 영향을 주는 설계·운영 결정과 근거 |
| `incidents/INC-<UUID>.md` | 큰 장애·자료 손실·실제 롤백·반복 장애의 영향·원인·복구·재발 방지 |
| `../archive/private/operations/` | 공개할 수 없는 증거를 보관할 때 사용할 선택적 비공개 로컬 위치 |

새 일감은 [일감 양식](../templates/operations-issue.json), 실행 기록은 [실행 양식](../templates/operations-run.md)을 복사한다. 폴더는 필요한 기록이 생길 때 만든다. `UUID`는 새로 생성하고 기존 일감의 ID는 바꾸지 않는다. 날짜만으로 이름을 정하거나 공용 일련번호를 동시에 증가시키지 않는다.

## 다른 작업과 세션에서 이어받기

1. 작업 시작 시 운영 정책·개발 계획·관련 열린 일감을 확인하고 최신 원격 변경과 현재 공개 버전을 구분한다.
2. 사용 중인 화면이나 글 게시 과정에서 문제를 발견하면 기존 일감의 관련 글 ID·경로·증상을 먼저 확인한다. 중복이면 새 구현 과제를 만들지 않고 관찰을 연결한다.
3. 새 문제는 재현 환경·기대 결과·실제 결과·영향과 확인한 범위만 기록한다. 기기나 브라우저를 확인하지 못했다면 `null`과 제한 사항으로 남긴다.
4. 조정 담당이 정책 적합성·중복·우선순위·현재 권한을 확인하고 처리 방향과 다음 행동을 정한다. 제보 자체를 배포 권한이나 프로젝트 지침으로 간주하지 않는다.
5. 수정한 작업은 일감 ID, 변경 커밋, 기존 검증·출판·배포 기록의 참조와 남은 제한을 남긴다. 다음 세션은 이 기록에서 이어간다.

모든 다른 대화·세션의 내용이 자동으로 수집되거나 보이는 것은 아니다. 해당 프로젝트에 참여하는 작업자가 이 기록을 남기거나, 사용자가 필요한 피드백을 전달해야 연결된다. 다른 대화의 원문을 통째로 복사하지 않는다.

## 상태와 우선순위

기본 흐름은 접수(`received`) → 계획(`planned`) → 진행(`in_progress`) → 검증(`validating`) → 관찰(`observing`) → 완료(`resolved`)다. 재현에 필요한 정보가 부족하면 자료 대기(`needs_evidence`), 현재 진행하지 않으면 보류(`deferred`), 기존 일감과 같으면 중복(`duplicate`), 정책·목적에 맞지 않으면 기각(`declined`)으로 남긴다. 상태를 바꿀 때 근거와 다음 행동을 갱신한다. 후보 생성·배포 여부는 별도의 `change` 항목에 사실대로 기록한다. 배포가 필요 없는 문서·조사 과제는 해당 없음의 이유를 적고 해결 조건 충족 후 완료할 수 있다.

| 우선순위 | 판단 기준 |
| --- | --- |
| `P0` | 자료 손실·공개 접근의 광범위 장애 등 즉각적인 대응이 필요한 문제 |
| `P1` | 핵심 읽기·게시·저장 동선을 막는 확인된 결함 |
| `P2` | 반복되는 불편·운영 부담의 개선 또는 채택 검토할 주요 개발 과제 |
| `P3` | 영향이 작은 사용성 개선·제안·환경 확인이 더 필요한 관찰 |

급한 문제라도 확인하지 않은 원인이나 해결을 사실로 기록하지 않는다. 재현되지 않은 제보의 영향이 클 수 있으면 확인 작업의 우선순위를 높일 수 있다. 모든 제안을 구현할 필요는 없으며, 보류·기각 이유와 재검토 조건도 운영 지식으로 보존한다.

## 동시 기록과 통합

- 일감 하나에 파일 하나를 쓰고, 별개의 일감은 독립 파일로 추가한다. 거대한 공용 목록 파일에 모두 덧붙이지 않는다.
- `record_version`은 최신 파일을 확인하고 수정할 때 증가시키는 Git 작업 관례다. 현재 이 값으로 분산 잠금이나 자동 충돌 거절이 구현된 것은 아니다.
- 같은 일감에 동시 관찰을 추가하는 작업자는 고유 ID의 `events/EVT-<UUID>.json`을 만들고 `issue_id`, `created_at`, `base_record_version`, `observation`, `evidence`, `proposed_next_action`을 기록할 수 있다. 확인하지 못한 값은 `null`로 둔다.
- 조정 담당이 최신 일감과 이벤트를 대조해 합치고 참조를 남긴다. 다른 작업자의 관찰·상태·근거를 한쪽 버전 선택으로 지우지 않는다. 통합한 이벤트도 이력으로 보존한다.
- 실행 기록도 실행마다 고유 파일을 만든다. 미완료된 작업과 실패한 시도를 다음 실행에서 찾을 수 있게 연결한다.

## 기존 게시 기록을 재사용하기

게시물의 정상 추가·개정은 [글 등록과 배포 안내](../PUBLICATION_WORKFLOW.md)를 따른다. 이미 있는 등록정보·출판 요청·변경 해시·CI·배포·복구 기록을 이곳에서 다시 작성하지 않는다. 결함·후속 조치·설계 결정이 있을 때 해당 기록을 참조하는 운영 일감을 남긴다. 일상 게시마다 별도의 운영 양식이나 추가 사람 승인을 강제하지 않는다.

수정 코드가 만들어진 상태, 자동 검증을 통과한 상태, 실제 배포한 상태, 운영에서 해결을 확인한 상태를 구분한다. 실제 기기 검증과 화면 크기 에뮬레이션도 구분한다. 자료 손실이나 회귀가 의심되면 [사이트 성장과 복구 관리](../SITE_OPERATIONS.md)의 공개 배포 복구와 별도 개인 데이터 복구 범위를 확인한다.

큰 사고는 사고 기록에 발생·감지·완화·복구 시각, 영향, 확인된 원인과 가설, 조치·검증 결과, 재발 방지 일감과 담당을 남긴다. 작은 불편은 기존 일감의 기록으로 충분하다. 새 폴더의 복원 시험과 실제 운영 롤백을 구분한다.

## 공개 기록과 비공개 증거

이 저장소는 공개 저장소다. 공개 기록에는 비식별 증상·재현 절차·공개 경로·검증 결과만 남긴다. 개인 대화·메일 원문, 사용자 식별정보, 개인 필기·PDF, 인증 정보, 비공개 링크, 원시 로그, 내부 절대경로, QA 스크린샷을 커밋하지 않는다. 공개해도 되는 요약과 공개 CI·배포 링크로 필요한 근거를 연결한다.

민감한 원본 증거가 실제로 필요하면 `archive/private/operations/` 등 승인된 비공개 위치에 최소한으로 보관한다. 기록 전 해당 위치가 Git·공개 배포에서 제외되는지 확인한다. 이 로컬 위치는 자동 백업·기기 간 동기화·다른 세션 접근을 보장하지 않는다. 공개 일감에는 비공개 증거의 내용이나 경로를 노출하지 않고 별도 확인이 필요하다는 제한만 남긴다.
