# 렉처 필기 동기화의 Cloudflare 비용 추정

기준일 **2026-11-04**, 통화 **USD**, 세금·환율 제외. 실청구서나 성능 측정 결과가 아닌 코드 기반 계획 모형이다. 실제 계정의 Free/Paid/Enterprise 플랜은 확인되지 않았다. 이 추산을 위한 유료 전환이나 새 리소스 생성은 없다. 공유 권한 개선은 기존 API와 사이트에 반영한다.

현재 페이지·공개 PDF는 **GitHub Pages 배포 + Cloudflare 프록시**이고, 계정·필기 API는 **Workers + D1**이다. Cloudflare Pages나 Workers Static Assets로 이전한 상태가 아니다. 로컬 PDF 바이트는 업로드하지 않으므로 현재 R2 PDF 저장 비용은 **$0**이다. 기존 알림·좋아요·로그·Queues·도메인·GitHub 요금은 아래 노트 모형의 범위 밖이며, 계정 단위 포함량을 다른 기능과 공유하면 추가 비용이 달라진다.

Workers 단가·CPU와 egress 조건은 [Workers 가격](https://developers.cloudflare.com/workers/platform/pricing/)과 [한도](https://developers.cloudflare.com/workers/platform/limits/)를 확인했다. D1 포함 읽기는 **2026-10-30 개정의 25B/월**을 적용했다. 행·인덱스 과금과 Free 초과 시 실패하는 동작은 [D1 가격](https://developers.cloudflare.com/d1/platform/pricing/), 한 DB 크기와 계정 합계 1 TB·쿼리 한도는 [D1 한도](https://developers.cloudflare.com/d1/platform/limits/)에 근거한다. Paid는 DB 100,000개까지 포함하고 이후 DB당 $0.10/월이지만, 여러 DB로 나누는 구조는 현재 구현하지 않았다.

[DO 가격](https://developers.cloudflare.com/durable-objects/platform/pricing/)은 incoming WebSocket 메시지 20개를 요청 1개로 환산하며, 유휴 hibernation 적격 시간에는 duration을 부과하지 않는다. DO 초과 요청·duration은 다음 백만 단위로 올림한다. [R2 가격](https://developers.cloudflare.com/r2/pricing/)의 단위 올림과 Standard 전용 포함량도 확인했다. R2 수치는 향후 별도 설계의 참고이며 현 추정액에는 넣지 않았다.

[Workers Static Assets](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/)와 [Cloudflare Pages의 정적 파일](https://developers.cloudflare.com/pages/functions/pricing/)은 해당 제품에서 정적 처리하면 요청이 무료·무제한이고 함수 실행은 별도다. 이 사실을 현재 GitHub Pages 트래픽의 Cloudflare Workers 무료 처리량으로 합산하지 않는다. Workers Static Assets에는 파일당 25 MiB 한도도 있어 PDF 배포 경로 변경 시 별도 검토가 필요하다.

## 2026-11-05 학습 공간 개선의 비용 범위

아래 DAU 표는 기존 필기 동기화 부하에 대한 모형이다. 새 학습 공간은 원본 PDF의 명시적 R2 보관, 사본·휴지통, 추가 패스키·초안 심사, 선택한 발표 페이지 따라가기를 추가했다. 파일 업로드·다운로드와 이 관리 동작의 빈도, 발표용 추가 조회·쓰기는 기존 표에 포함하지 않았다. 브라우저 저장은 PDF 바이트와 가변 metadata를 분리해 매 획의 원본 재기록을 없앴다. 이 기기 I/O 개선을 Cloudflare 과금 할인으로 계산하지 않는다.

원본 파일은 50 MiB/개, 업로더 총 500 MiB로 제한하고 휴지통의 원본도 보관량에 포함한다. [R2 Standard 요금](https://developers.cloudflare.com/r2/pricing/)은 월 10 GB-month·Class A 100만 회·Class B 1,000만 회 무료 포함 후 $0.015/GB-month, $4.50/백만 A, $0.36/백만 B이며 전송 egress는 무료다. 다른 앱의 계정 사용량과 합산되므로 이 앱의 무제한 무료 보관을 약속하지 않는다. R2 연결·구독의 실제 상태는 운영 계정에서 확인해야 하며, 현재 기본 배포 설정에는 파일 보관 binding을 넣지 않았다.

임시 객체에 스트리밍·해시 검증한 뒤 불변 원본을 확정하므로 파일 한 번의 업로드는 단순 PUT 한 번과 같은 연산 수가 아니다. 50 MiB 업로드의 실제 Worker CPU는 미측정이며 Free의 10 ms 충족을 보장하지 않는다. 원본·변경 로그는 자동 만료하지 않으며, 사본/새 학습본은 기존 노트를 남기므로 D1 보관량도 증가할 수 있다. 현재 한 DB의 10 GB 한도와 아래 용량 경고는 계속 적용된다.

## 계산 입력

동일한 100·1,000·10,000명이 매일 30분씩 30일 사용하고, 각자 노트 한 권에 하루 새 획 500개와 그중 20%인 지우기 100개를 만든다. 저장되는 획 JSON은 평균 **1 KB = 1,000 bytes**로 가정했다. 합성 입력이며 실제 필기에서 측정하지 않았다.

- 기본은 **1개 작업마다 동기화**한다. 100개는 API 최대 배치 크기이며 평소 묶음 크기라고 가정하지 않는다.
- `atr:notes-saved`는 250 ms 뒤 동기화를 예약하고, 완료 뒤 4초 유휴 타이머를 다시 건다. 600개 작업을 30분에 균등 배치하면 3초마다 저장하므로 유휴 4초 poll은 취소된다. 동기화마다 변경 GET → 작업 POST → 변경 GET을 센다.
- 읽기만 하면 4초 poll 예산은 **450회/30분**이다. 여기에 모든 쓰기 전후 GET을 무조건 더하면 겹쳐 센다. 모형은 균등한 합성 이벤트 시각으로 타이머 재예약을 계산한다. 네트워크 지연은 0으로 둔 요청 수 모형이다.
- 위치·책갈피가 바뀌는 저장은 하루 30회로 가정하고 기존 주기에 추가 POST를 센다. 변화가 없으면 현재 코드는 위치를 쓰지 않는다. 로그인 1회/일(옵션·검증 2회), 열기 3회(`/me`, 목록, snapshot), CORS preflight 5회/일, 첫 달 가입·노트 연결 6회를 별도 예산으로 잡았다.
- 매일 snapshot 한 번은 보수적 가정이다. 브라우저가 원격 캐시를 보존하면 줄고, 여러 기기·잦은 재연결·공유 수업의 읽기 fanout은 늘린다. 현재 metadata 갱신을 별도 poll API로 중복 계산하지 않는다.

## 최종 구현의 D1 비용 구조

`src/study.js`, migration `0004`와 `0005`, `cloud.mjs`를 기준으로 계산했다. 새 획은 `study_strokes`와 `study_changes`에 각각 기록되고 기존 trigger가 `study_notebooks`를 갱신한다. 모형의 새 획당 **5행 쓰기**는 이 3개 논리 쓰기와 2개 인덱스 쓰기, 기존 획 지우기당 **4행**은 3개 논리 쓰기와 변경 이력 인덱스를 가정한 값이다. 권한 trigger의 membership·기존 획 조회도 읽기에 포함했다. rate-limit·위치·인증·정리 쓰기를 더해 기본 하루 약 **3,590행/사용자**, 첫 달 가입 추가 33행/사용자를 센다.

이 값은 운영 `meta.rows_read/rows_written`의 측정값이 아니다. 쿼리 계획·인덱스·trigger·SQLite 내부 기록에 따라 달라질 수 있어 코드의 계수를 조절할 수 있다. 인덱스가 있는 빈 poll도 세션·멤버십 조회를 하므로 DB 사용량 0으로 두지 않았다.

승인된 `0005` 개선은 `stroke_count`, `ink_bytes`를 기존 노트 UPDATE 안에서 유지한다. **매 저장의 전체 노트 COUNT/SUM 스캔은 제거되었고**, 현재 표에는 PK 조회를 적용했다. 과거 구현이었다면 30일 동안 사용자당 약 141.73M행을 추가 스캔했을 가정이다. 이 제거된 비용을 현 운영 병목이나 현 청구량으로 표시하지 않는다. 초기 backfill은 한 번 실행하는 마이그레이션 비용으로, 일상 트래픽 표에 반복해서 넣지 않았다. 또한 최대 100개 작업의 기존 획 조회를 bound JSON 한 건과 복합 기본키 조회로 묶어, 획마다 D1 binding 호출을 만들지 않도록 했다. 이 변경은 Free의 invocation당 50회 호출 한도 안에서 큰 동기화 배치도 처리하게 하며, 실제 읽은 행 수가 무료가 된다는 뜻은 아니다.

읽기 기본 추정은 빈 변경 GET당 6행, 작업 POST당 고정 8행, 개별 작업당 6행, 실제 반환한 변경과 snapshot의 보관 획 수다. 현재 읽기는 인덱스·counter를 쓰지만, **전체 snapshot 자체는 노트 전체 획·tombstone을 읽는다**.

## 보관량과 보존 기간

사용자당 30일 새 획은 15,000개다. 20% 지우기를 적용한 활성 JSON은 12 MB지만, 이전 put의 JSON은 변경 이력에 15 MB 남는다. 따라서 **payload만 27 MB/사용자**다. DB 추정에는 추가로 테이블·인덱스·키·빈 공간을 포함하는 **1.25배 계수**와 사용자 metadata 8 KB를 가정했다. 1~2배 민감도를 별도로 계산할 수 있고, 실제 `database_size`로 교체해야 한다. 평균 보관량은 첫날 빈 DB에서 쌓이는 일말 보유량의 평균 근사다. 말일 크기 전체를 한 달 저장했다고 과금하지 않았다.

실행 시점의 비식별 집계에서 계정·노트·획·변경 이력은 0이고 기존 DB 크기는 364,544 bytes였다. 이 값만 모형의 초기 크기로 사용했으며 계정 주소·필기 원문은 수집하거나 보고서에 넣지 않았다. 이 집계는 플랜이나 앱 CPU 벤치마크를 확인한 결과가 아니다.

자동 이력 보존 기한·정리 정책은 없다. 지운 획의 이전 payload도 변경 로그에 남으므로 보관량은 활성 JSON만으로 계산하면 작아진다. 다만 한 노트는 **25,000개 stroke ID/tombstone**, **활성 JSON 12 MB**에 제한되어 무한히 새 획을 받아들이지는 않는다. 이 부하에서는 12 MB에 30일, 25,000 ID에 50일이 걸린다. 후자는 앞의 활성 JSON 제한으로 이미 쓰기가 거부될 수 있는 산술값이다. 여러 노트·계정의 보관은 계속 누적되며 현재 계정당 소유 노트 한도는 100권이다. 모형의 60일 계산은 한도를 해제한 외삽으로 구분한다.

## 향후 공동 수업: DO hibernation 비교

현재는 WebSocket 수업이나 DO를 구현·이전하지 않았다. 미래에 노트/수업 단위 DO가 변경을 전달한다고 가정하면 4초 poll을 없앨 수 있지만 인증·권한·저장·충돌 처리는 여전히 필요하다.

하루 연결 1개, incoming 작업 메시지 600개, hibernation을 쓴다는 **전송 부분만의 가정**에서 다음 DO 요금이 나온다. Workers 연결·인증 요청/CPU와 D1 또는 DO SQLite 행·저장 요금은 포함하지 않는다.

| DAU | DO 과금 요청 단위/월 | handler 10 ms일 때 GB-s | DO 요청+duration | handler 100 ms일 때 요청+duration |
| ---: | ---: | ---: | ---: | ---: |
| 100 | 93,000 | 2,304 | $0 | $0 |
| 1,000 | 930,000 | 23,040 | $0 | $0 |
| 10,000 | 9,300,000 | 230,400 | $1.35 | $26.35 |

handler 시간도 미측정이다. DO duration에는 I/O를 포함한 실제 활성 wall-clock이 들어가며 방별 동시 처리와 사용자 수에 따라 달라진다. hibernation 없이 사용자별 객체를 30분 내내 유지하면 1,000 DAU의 duration만 약 **6,912,000 GB-s → $87.50**로 바뀐다. DO로 전달만 옮기면 현재 D1의 획·변경 이력 중복 저장은 그대로다. DO SQLite나 R2 스냅샷으로 저장 설계까지 바꾸는 비용·정합성·수업 fanout은 별도 모델이 필요하다.
